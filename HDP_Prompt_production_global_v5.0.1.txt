PROMPT GLOBAL DE PRODUCTION - HUMANITARIAN DATA PLATFORM V5.0.1

OBJECTIF
Construire, tester et emballer HDP V5 comme application locale installable Windows x64 et déploiement Linux Docker Compose, sans régression des fonctions V4.

ARCHITECTURE
- conserver un monolithe modulaire FastAPI/PostgreSQL/PostGIS ;
- isoler les domaines acquisition, intelligence HDX, scripts/notebooks et présentation ;
- éviter tout microservice sans frontière de sécurité ou besoin de montée en charge démontré ;
- exécuter Python/R dans des runners sans réseau et avec une identité distincte par job.

FONCTIONS OBLIGATOIRES
- recherche fédérée et acquisitions POST traçables ;
- HDX Data Grid par périmètre, localisation, période, format et dimension ;
- descriptions jeu/fichier : structure, noms, types, dates, périodicité, échéance et fiabilité transparente ;
- plan d’agrégation avec contrôles géographiques, temporels, unités, licences et lignée ;
- ingestion/déduplication/règles SIGNALS depuis HDX Signals, RSS, news, GDACS et webhooks ;
- recherche Data Grid automatique sur événement et mise à jour uniquement si l’échéance attendue est atteinte ;
- surveillance syndromique globale ou locale, non diagnostique, preuves conservées ;
- prompts SIGNALS contraints aux preuves, contradictions et incertitudes ;
- notebooks Jupyter nbformat 4.5, Python/R, versions SHA-256, confirmation avant exécution ;
- documentation, UML, Wiki versionné et liens externes repliables dans l’interface.

SÉCURITÉ NON NÉGOCIABLE
- token local >= 32 caractères, cookie HttpOnly, contrôle Host/Origin/CSRF ;
- aucune mutation via GET ;
- SQL analysé par AST, vues limitées au projet, rôle hdp_reader non privilégié ;
- téléchargements HTTP avec IP publique validée et épinglée, redirections revalidées ;
- sauvegarde sans secrets, SHA-256 externe, manifeste interne et validation avant extraction ;
- conteneurs non-root et en lecture seule sauf volumes explicitement nécessaires ;
- aucun script lancé automatiquement sur un signal sans politique et confirmation explicites.

QUALITÉ ET LIVRAISON
- boucler code -> tests -> audit -> corrections jusqu’à une suite verte ;
- compiler runner.c avec -Wall -Wextra -Werror ;
- analyser Python et JavaScript ;
- construire l’EXE dans un runner Windows, vérifier PE32+ et publier SHA-256 ;
- produire archive complète contenant EXE, payload Windows/Linux, docs, UML PDF, Wiki, SBOM et rapport de validation ;
- ne jamais annoncer « validé » pour un test non exécuté ; documenter tout blocage de plateforme ou de signature.

CRITÈRES D’ACCEPTATION
Chaque fonction dispose d’un test automatisé ou d’un scénario de recette documenté. Une recherche sur signal produit une action traçable. Un notebook exécute une cellule confirmée. Une restauration corrompue est refusée avant modification. L’interface expose les liens sans densifier la navigation principale. Les archives et l’EXE sont vérifiables par SHA-256.
